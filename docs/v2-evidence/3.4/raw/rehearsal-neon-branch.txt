== Step C: lock measurement (single transaction) ==
  ALTER TABLE user_institution_memberships VALIDATE CONSTRAINT memberships_user_id_fk;
  SELECT c.relname, l.locktype, l.mode, l.granted FROM pg_locks l
    JOIN pg_class c ON c.oid=l.relation
   WHERE c.relname='user_institution_memberships' AND l.locktype='relation';
 ->  user_institution_memberships | relation | AccessShareLock            | t
     user_institution_memberships | relation | ShareUpdateExclusiveLock   | t
MEASURED LOCK: ShareUpdateExclusiveLock (design.md §19 "bounded locks" control).
ShareUpdateExclusive does NOT conflict with AccessShare/RowShare/RowExclusive, so
concurrent SELECT / INSERT / UPDATE / DELETE keep running during validation; it
only conflicts with DDL / VACUUM / another ShareUpdateExclusive. Online-safe; runs
inside the normal transactional apply_sql_migrations path (no CREATE INDEX
CONCURRENTLY needed). VALIDATE CONSTRAINT is transaction-safe.
