The bullet says "deploy ... to a canary tenant". Three facts decide what that
sentence can mean here, and all three are in the repository.

---------------------------------------------------------------------------
FACT 1 - there is exactly ONE Compose project, so there is no traffic split.
---------------------------------------------------------------------------
deploy/docker-compose.prod.yml defines six services on one host:
  caddy (the only service with published ports 80/443)
  web · celery · beat · redis · postgres

  $ grep -c '^  [a-z]*:$' deploy/docker-compose.prod.yml
    6 services, one postgres, one web

The deploy workflow (.github/workflows/deploy.yml) pins ONE backend image and
ONE frontend image into ~/mihas/.env and runs `compose up -d`:

    pin_env BACKEND_IMAGE  "${NEW_BACKEND}"
    pin_env FRONTEND_IMAGE "${NEW_FRONTEND}"
    ${COMPOSE} pull   || rollback "image-pull"
    compose_up        || rollback "container-start"

There is no second web service, no weighted upstream, no percentage split, and
no per-tenant image. CONSEQUENCE: code and schema are deployed for EVERY tenant
at the same instant. A canary cannot contain the code.

What the deploy DOES give is a real, tested rollback anchor: PREV_BACKEND /
PREV_FRONTEND are captured before the pull, and the `rollback()` trap re-pins
and restarts them. Note in particular:

    # Re-pin .env to the last-good images and restart. No `down`, no
    # `-v`: the postgres volume and DB are left completely untouched.

So the reversible unit is THE IMAGE PAIR, not the tenant.

---------------------------------------------------------------------------
FACT 2 - the edge serves exactly three fixed hostnames. A tenant hostname
         pointed at this box is NOT served.
---------------------------------------------------------------------------
apps/admissions/Caddyfile has three site blocks and nothing else:

    {$APP_HOST}  { ... SPA at /srv/www ... }
    {$API_HOST}  { reverse_proxy web:8000 }
    {$JOBS_HOST} { ... SPA at /srv/jobs ... }

  $ grep -n "on_demand\|ask\|^\*\." apps/admissions/Caddyfile
    (no on-demand TLS, no wildcard site, no ask endpoint)

Each is a single env-var hostname supplied by compose:

    APP_HOST:  ${APP_HOST:?set APP_HOST e.g. apply.beanola.com}
    API_HOST:  ${API_HOST:?set API_HOST e.g. api.beanola.com}
    JOBS_HOST: ${JOBS_HOST:?set JOBS_HOST e.g. jobs.beanola.com}

CONSEQUENCE: adding a tenant hostname requires (a) a DNS A record, (b) a new
Caddy site block or on-demand TLS, and (c) a rebuild of the FRONTEND image,
because the Caddyfile is baked into it (apps/admissions/Dockerfile). None of
that is configured today, so a per-hostname canary is not a configuration
change - it is a code change to the edge.

---------------------------------------------------------------------------
FACT 3 - today every request resolves to the NEUTRAL Beanola context, and the
         production lineage has zero domain rows.
---------------------------------------------------------------------------
Tenant resolution reads the host:

    backend/apps/catalog/_catalog_view_helpers.py:379
      def _request_host(request):
          return request.headers.get("X-Forwarded-Host") or request.get_host()

and InstitutionContextService.resolve binds a tenant ONLY when exactly one
InstitutionDomain with status='active', is_active=true, on an active
institution matches. Two things follow.

(a) The two production hostnames are REGISTERED NEUTRAL PORTAL HOSTS:

    backend/config/settings/base.py:43
      SHARED_PORTAL_HOSTS = split_csv_env("SHARED_PORTAL_HOSTS",
        "apply.beanola.com,api.beanola.com,localhost,127.0.0.1,testserver,web,0.0.0.0")

    So a request arriving at api.beanola.com is the SHARED Beanola portal, and
    an explicit institution selector is honoured only on such a host and only
    on an allow-listed endpoint (`resolved_institution_id`).

(b) On the restored production-lineage snapshot there are NO domain rows at all
    (preflight gate 23, raw/preflight-two-databases.txt):

      gate23 resolvable host inventory | domain_rows 0 | marked_active 0
                                       | resolves_a_tenant 0

CONSEQUENCE: the platform runs today as the shared Beanola portal. A tenant is
selected per application (through the offering the student picks), not by
hostname. A host-scoped canary would have to be CREATED - a domain row plus the
edge change in FACT 2 - and creating it is a production write.

---------------------------------------------------------------------------
SO WHAT IS THE CANARY? The only lever the platform actually has.
---------------------------------------------------------------------------
Preflight gate 24, on the production-lineage snapshot:

  gate24 open-intake exposure by tenant
   institution_code | institution_active | offerings | open_intakes | drafts | submitted+
   KATC             | t                  |         2 |            2 |      0 |          0
   MIHAS            | t                  |         2 |            2 |      0 |          0

TWO tenants are simultaneously able to receive a new application. That is the
blast radius, and it is also the lever: the canary is TENANT ACTIVATION - which
institution's offerings have an open intake that will accept a new application.

  canary        = exactly ONE institution with open_intakes > 0
  broaden       = re-open the second institution's intakes
  contain       = close them again (a catalogue write, reversible, no data loss)

This is weaker than a traffic-split canary and the difference must not be
papered over: V2 code and the expanded schema serve BOTH tenants from the
moment the image rolls. What tenant activation contains is the population that
can create NEW state through the new write paths - which is exactly the
population the nine monitored signals are about.
