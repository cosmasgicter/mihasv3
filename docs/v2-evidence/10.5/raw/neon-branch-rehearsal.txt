3. The partial unique index actually constrains (and only issued rows)
================================================================
Run as one DO block whose final RAISE aborts the block, so NOTHING
persists — the assertion is which exception fires.

  DO $$
  DECLARE a uuid; b uuid;
  BEGIN
    SELECT id INTO a FROM applications ORDER BY created_at LIMIT 1;
    SELECT id INTO b FROM applications WHERE id <> a ORDER BY created_at LIMIT 1;
    UPDATE applications SET tracking_selector='TESTSEL1' WHERE id = a;
    BEGIN
      UPDATE applications SET tracking_selector='TESTSEL1' WHERE id = b;
      RAISE EXCEPTION 'FAIL_DUPLICATE_SELECTOR_WAS_ACCEPTED';
    EXCEPTION WHEN unique_violation THEN
      RAISE EXCEPTION 'OK_DUPLICATE_REJECTED_AND_NOTHING_PERSISTED (31 NULL selectors coexisted)';
    END;
  END $$;

  NeonDbError: OK_DUPLICATE_REJECTED_AND_NOTHING_PERSISTED
               (31 NULL selectors coexisted)

i.e. a second live selector with the same value is rejected, while the
other 31 rows hold NULL selectors simultaneously — which a plain
column-level UNIQUE could not express as cheaply and which is why the
model field is deliberately NOT declared unique=True.

Confirming nothing persisted:
  SELECT count(*) rows_total, count(tracking_selector) selectors_persisted
    FROM applications;
  -> rows_total = 33, selectors_persisted = 0
