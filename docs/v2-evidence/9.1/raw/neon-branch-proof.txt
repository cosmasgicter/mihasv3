1. Re-running the forward script is a no-op (idempotence)
--------------------------------------------------------------------------------
All six statements of the forward script were re-executed on the branch, in one
transaction, against a database where the table already existed:

  CREATE TABLE IF NOT EXISTS admin_saved_filters (...)
  CREATE UNIQUE INDEX IF NOT EXISTS uq_admin_saved_filters_owner_name ...
  CREATE INDEX IF NOT EXISTS idx_admin_saved_filters_owner_updated ...
  CREATE INDEX IF NOT EXISTS idx_admin_saved_filters_institution ...
  COMMENT ON TABLE admin_saved_filters IS ...
  COMMENT ON COLUMN admin_saved_filters.query IS ...

  -> [[], [], [], [], [], []]        (six statements, no error, no change)

Every statement is guarded, so a re-run after a migration-tracking wipe converges
rather than failing. This is the property `apply_sql_migrations` relies on.

2. The table Postgres actually built
--------------------------------------------------------------------------------
SELECT column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_name='admin_saved_filters' ORDER BY ordinal_position;

 column_name    | data_type                   | is_nullable | column_default
----------------+-----------------------------+-------------+-------------------
 id             | uuid                        | NO          | gen_random_uuid()
 user_id        | uuid                        | NO          | (none)
 institution_id | uuid                        | YES         | (none)
 name           | character varying           | NO          | (none)
 query          | jsonb                       | NO          | '{}'::jsonb
 created_at     | timestamp with time zone    | NO          | now()
 updated_at     | timestamp with time zone    | NO          | now()

`institution_id` is the only nullable column: NULL means "not bound to one
school" (a platform actor's cross-tenant view). Both timestamps default in the
database, so a row is never written without them.

3. Indexes
--------------------------------------------------------------------------------
SELECT indexname, indexdef FROM pg_indexes
WHERE tablename='admin_saved_filters' ORDER BY indexname;

 admin_saved_filters_pkey
   CREATE UNIQUE INDEX admin_saved_filters_pkey
     ON public.admin_saved_filters USING btree (id)
 idx_admin_saved_filters_institution
   CREATE INDEX idx_admin_saved_filters_institution
     ON public.admin_saved_filters USING btree (institution_id)
     WHERE (institution_id IS NOT NULL)
 idx_admin_saved_filters_owner_updated
   CREATE INDEX idx_admin_saved_filters_owner_updated
     ON public.admin_saved_filters USING btree (user_id, updated_at DESC)
 uq_admin_saved_filters_owner_name
   CREATE UNIQUE INDEX uq_admin_saved_filters_owner_name
     ON public.admin_saved_filters USING btree (user_id, lower((name)::text))

The unique index is on `lower(name)`, which is what makes "Overdue" and
"overdue" one saved view instead of two rows an operator cannot tell apart.

4. Constraints
--------------------------------------------------------------------------------
SELECT conname, confdeltype, pg_get_constraintdef(oid)
FROM pg_constraint WHERE conrelid = 'admin_saved_filters'::regclass;

 admin_saved_filters_institution_id_fkey | c | FOREIGN KEY (institution_id)
                                               REFERENCES institutions(id)
                                               ON DELETE CASCADE
 admin_saved_filters_pkey                |   | PRIMARY KEY (id)
 admin_saved_filters_user_id_fkey        | c | FOREIGN KEY (user_id)
                                               REFERENCES profiles(id)
                                               ON DELETE CASCADE

`confdeltype = 'c'` on both FKs: a deleted actor or a deleted tenant leaves no
orphan saved query behind.

5. The uniqueness claim, exercised
--------------------------------------------------------------------------------
-- (a) one owner saves a named, school-bound view
INSERT INTO admin_saved_filters (user_id, institution_id, name, query)
SELECT <first profile>, <first institution>, 'Overdue', '{"overdue_review":"true"}';
  -> id = 239dacc2-fabb-4cd3-b3f0-2143943d47ab, name = 'Overdue',
     query = {"overdue_review": "true"}, created_at populated

-- (b) the SAME owner saves the same name in different case
INSERT INTO admin_saved_filters (user_id, name, query)
SELECT <first profile>, 'overdue', '{}';
  -> NeonDbError: duplicate key value violates unique constraint
     "uq_admin_saved_filters_owner_name"

     This is the guard the service relies on: `POST saved-filters/` treats a
     repeated name as an UPDATE, and the database is the final race guard if two
     concurrent saves pick the same name (the view catches IntegrityError and
     converges on the existing row).

-- (c) a DIFFERENT owner saves the same name
INSERT INTO admin_saved_filters (user_id, name, query)
SELECT <second profile>, 'Overdue', '{"overdue_review":"true"}';
  -> id = f8992e29-b44e-436c-8749-17656c463918,
     user_id = 6e147ead-e34d-41e2-bc05-358a653ff633, institution_id = NULL

     Uniqueness is per owner, not global: two operators may each have their own
     "Overdue" view, and a saved filter with no school binding is legal.
