The two cases that carry the comment's promise:

  TestInvariantSqlMatchesTheProjectionItClaimsToCheck
    ::test_sql_encodes_the_precedence_in_declared_order[path0]   invariants.sql
    ::test_sql_encodes_the_precedence_in_declared_order[path1]   the contract migration

  Parametrised over BOTH files deliberately. The invariant queries and the
  contract migration each reimplement APP_PAYMENT_STATUS_PRECEDENCE in SQL —
  they have to, because they run inside the database, including on production
  where no Python runs. Two reimplementations of one constant are two
  opportunities to drift, so the same assertion covers both. It checks
  membership (every derived value and every ledger status is named) AND ORDER
  (the CASE branches appear in the constant's declared, highest-precedence-first
  sequence), because an application holding both an expired and a successful
  payment projects differently if the order moves.

  Verified by breaking it on purpose, because a guard nobody has seen fail is
  not a guard. The `deferred` and `pending_review` branches were swapped in
  invariants.sql's FIRST projection CASE only — a change that leaves every
  status still present, so only the ORDER assertion can catch it:

    $ pytest ...::TestInvariantSqlMatchesTheProjectionItClaimsToCheck -q
