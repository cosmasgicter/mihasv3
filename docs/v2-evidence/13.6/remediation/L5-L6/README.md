## 1. L5 — the root cause was a missing branch, not a broken read

### 1.1 What 13.3 found

`/student/status` is a registered canonical route (`routeRegistry.ts` →
`student.status`), it is what the nav item points at, and
`/student/application-status` **redirects to it**. Task 13.3 loaded it as a student
who owned two applications — one draft, one submitted — and was told:

> **Application Status** · Application Not Found · *Application not found or access
> denied* · Try Again · Contact Support

That is **GATE-13.3-09**, and it is why register finding **STU-23 (P1)** was not
closed even though task 10.6 is `[x]`.

### 1.2 The cause, traced

Four registered paths reach this route and **only three carry an `:id`**:

```
/student/status                          <-- no id  (the nav item, and the redirect target)
/application/:id
/student/application/:id/status
/student/application/:id                 <-- DuplicateRouteRedirect
```

`ApplicationStatus` read that id with `useParams` and handed it to
`useApplicationWorkspace(id, !!user)`, whose detail read is gated
`enabled: !!id && enabled`. On the bare path `id` is `undefined`, so:

| step | value |
|---|---|
| React Query `enabled` | **false** — the request never went out |
| `isLoading` | **false** — a *disabled* query is pending but not fetching |
| `application` | `null` |
| `error` | `''` |
| `if (error \|\| !application)` | **true** → the error branch |

So an absent **parameter** was reported as an absent **application**. Four
candidate causes were checked and three ruled out:

| candidate | verdict |
|---|---|
| the route's **data fetch** | no — the fetch is correct and never ran |
| the route's **param handling** (10.6 consolidated several routes and redirects a duplicate) | **yes** — this is it. 10.6's redirect and aliases are all correct; the *bare* path had no branch |
| **the canonical-id reads L1 changed** | **no**, and this was verified rather than assumed. L1 changed five *backend* read sites (`canonical_reads.py` + 5 callers) that resolve an intake/offering from an application row. This route never reached the server at all — `enabled` was false — so no backend read, canonical or otherwise, participates. `git log`/diff of L1's files shows no frontend file among them, and the reproduction predates L1 (13.3 ran on `bae29a28d`) |
| the **empty-state branch itself** | no — it renders exactly what it was asked to render. `ErrorDisplay` is behaving correctly; it was handed an error state for a page that had no error |

### 1.3 The fix

`/student/status` now has two shapes, and **the workspace itself is untouched**:

* **no id** → `ApplicationWorkspaceIndex` (new,
  `src/components/student/applicationStatus/ApplicationWorkspaceIndex.tsx`). It reads
  the student's own applications — the same `applicationService.list({ mine: true })`
  the dashboard and `/student/payment` already use, under its own cache key
  `['student-status-index', userId]` — and then:

  | owned | behaviour |
  |---|---|
  | 0 | a real empty state offering the one thing there is to do: start an application |
  | 1 | `replace`-navigate to that application's workspace, so one application still has exactly one workspace URL (R13.13) |
  | 2+ | **a chooser** — every application with its status pill and a link to its own workspace |

* **an id** → `ApplicationWorkspaceView`, which is this file's original body verbatim,
  except that `id` arrives as a prop it can rely on.

**Why a chooser and not "the most recent".** `.kiro/steering/enterprise-tenancy.md`
("Student Draft Lifecycle") already settles the same question for the wizard:
*"Direct wizard visits with existing drafts must show a choice or follow a documented
deterministic contract; they must not silently pick an old draft by timestamp."*
Picking one of two applications by recency here would be that same silent choice, on
the one surface whose job is telling a student where each application stands.

## 3. GATE-13.3-07 — the CLS was two insertions, and the arithmetic named them

13.3 proved it was not flake: 375 px read 0.1172 / 0.1188 / 0.1164 / 0.1164 across
four separate runs, always over the 0.100 budget, while 320 / 768 / 1280 / 1440 and
the whole wizard were inside it. One surface, two widths.

**1. `NextActionPanel`'s loading state had no size.** While readiness was in flight
it rendered an eyebrow and a heading and *nothing else*; when the answer landed it
grew by a two-line blocker sentence **plus a 68 px primary control** — ~90 px
appearing at the very top of the page at t ≈ 600 ms and pushing every section below
it down. Against a 667 px viewport that is a distance fraction of ~0.135, and at an
impact fraction near 0.85 the product is ~0.11. **That is the number that was
measured.** The loading state now occupies the resolved state's box: a real detail
sentence, and a `min-h-touch-lg` placeholder in the action row (`aria-hidden`, because
the panel already announces *"Checking what is outstanding"* through its own
`role="status"` region).

**2. The refresh progress bar was in the flow.** It was the first child of a
`space-y-6` stack, so every poll inserted and removed ~28 px (a 4 px bar plus a 24 px
gap) at the top of the content — and polling is enabled the instant the initial load
completes, which is the same window. It is `absolute` inside a `relative` wrapper now
and contributes nothing to layout; `role="status"`, `aria-live="polite"` and the
`sr-only` sentence are unchanged, so what a screen-reader user hears is the same.

Result — all twelve readings, both profiles:

```
                 320      375      390      768     1280     1440
before        0.0851   0.1164   0.1046   0.0850   0.0544   0.0485
after         0.0222   0.0406   0.0357   0.0431   0.0333   0.0129
```

**The dashboard CLS is 0.0406 at 375 and 0.0357 at 390.** The worst reading anywhere
in the sweep is 0.0431 — under half the budget — and `KNOWN_CLS_OVER_BUDGET` is empty,
so any over-budget reading at any width on any surface now fails the row.

## 4. The three findings that were really one line each, and the two that were not

### 4.1 GATE-13.3-08 — including the half 13.3 said it had not traced

13.3 measured a heading *before* the `h1` on three surfaces and said, honestly, that
it had **not** attributed it to a component. It is `ui/MobilePageHeader.tsx`: the page
title was an `h2` in a bar the shell mounts **before** `main`, so every authenticated
surface opened `h2 → h1`. One shell cause, three surfaces — exactly as 13.3 predicted
by keying its allow-list to `/student/` rather than to a route.

It is a `<p>` now. A page has one accessible title and `PageShell` already renders it
as the `h1`; this bar *restates* it for orientation on a 64 px header, which is a
label's job. The visible text is unchanged, it is still announced in reading order,
and it is no longer an earlier, higher heading competing with the page's own.
`aria-hidden` would have been wrong (a screen-magnifier user reads it) and `h3` would
still have preceded the `h1`.

The other two: `ApplicationListItem.tsx`'s `h4` → `h3` (it sits inside a `SectionCard`
whose title is an `h2`; the size comes from `text-sm`/`sm:text-base`, never the tag),
and `ErrorDisplay`'s hardcoded `h3` → a `headingLevel` prop defaulting to `h2`, so a
page-level error follows the page's `h1` while a caller nesting it inside a
`SectionCard` can still pass `h3`.

**Measured after, all three surfaces × both profiles: `h1=1  beforeH1=0  skips=[]`.**

### 4.2 GATE-13.3-12 — nine axe rows from two token misuses

| element | pair | measured | now |
|---|---|---|---|
| bottom-nav active label, *More* label, 5 Education-step chips | `bg-primary/10` + `text-primary` | **4.49 : 1** — marginally under AA, at 10–12 px so no large-text allowance | `bg-accent text-accent-foreground` = **7.2 : 1** |
| *"Recommended subjects for …"* heading | `text-primary-foreground` on `bg-primary/5` | **white on near-white**, ~1.1 : 1 — not a marginal miss | `text-accent-foreground` |
| the *"n/5 unique minimum"* counter | `text-red-500` / `text-green-600` | **3.76 : 1**, and a **raw palette step on a status message**, which `DESIGN.md` forbids independently of contrast | `text-destructive` / `text-success` **with an icon**, because a status is never colour alone |
| both `text-[10px]` nav labels | — | below the type scale's floor (`xs` = 12 px) | `text-xs` |

**No token was invented.** `accent` (#dbeafe) / `accent-foreground` (#1e40af) are
already in `src/styles/design-tokens.css`, as the pair for a tinted surface with an
accessible foreground. axe `color-contrast`: **24 nodes → 0**.

The heading was also *looked at* afterwards, and that mattered: the counter's
`inline-flex` badge is an atomic box, so at 320 px the heading broke as
`Grade 12 Subjects (` / `0/5 unique minimum` / `)` with the closing bracket orphaned
on its own line. A progress count is a status, not part of a section's name, so it is
its own line now. The **string is deliberately unchanged** —
`tests/harness-e2e/required/ocr-manual-fallback.spec.ts:217,252` locates this counter
by its exact text while walking the OCR-confirmation journey, and that spec is the
wizard lane's.

### 4.3 GATE-13.3-14 — the config was right, so the config was not touched

13.6 §8.1 asked for the cause rather than another config edit, and the cause was one
line: `src/index.css`'s `body` rule hardcoded `font-family: Inter, system-ui,
sans-serif` inside `@layer base`, shadowing the utility the config feeds. `@apply
font-sans` emits `theme.fontFamily.sans` verbatim, so the rendered chain is now *by
construction* whatever the config says and cannot drift from it again.

The other two candidates 13.6 named were checked and eliminated: the only remaining
`font-family` declarations in the app's CSS are the `@font-face` that **defines**
Inter (`src(local('Inter'))` — it declares a family, not a chain) and one on
`index.html`'s pre-mount `.beanola-preloader` element, which is removed before the app
renders and is not on `body`. No build-time transform is involved — the emitted
stylesheet carries the full chain:

```
$ grep -o "font-family:Inter[^};]*" dist/index.html
font-family:Inter,ui-sans-serif,system-ui,-apple-system,BlinkMacSystemFont,Segoe UI,Roboto,Helvetica Neue,Arial,Noto Sans,sans-serif
```

**And it resolves fully in the browser**, which is the claim that matters:

```
before  getComputedStyle(body).fontFamily -> ['Inter','system-ui','sans-serif']            (3 of 11)
after   getComputedStyle(body).fontFamily -> ['Inter','ui-sans-serif','system-ui',
          '-apple-system','BlinkMacSystemFont','Segoe UI','Roboto','Helvetica Neue',
          'Arial','Noto Sans','sans-serif']                                                (11 of 11)
```

The converted row asserts equality against the declared list, not just
`toContain('Noto Sans')` — a chain that reached `Noto Sans` by dropping something else
would now fail. The declared list is **written out in the spec** rather than imported
from `tailwind.config.js`, because importing the file under test is how the green
guard 13.3 §8.14 found came to be tautological.

### 4.4 GATE-13.3-15 — a control compliant only because of a media query is not compliant

The reason it appeared only at ≥ 768 px is exact and is the interesting half:
`src/index.css` scopes the platform's 44 px form-control floor to
`@media (max-width: 639px)`, so a global rule rescued three raw
`<select>`/`<input>`/`<textarea>` on phones and **nothing** did at 768 px and above
(measured 414×37/38, 579×37/38, 686×37/38 — the width tracked the container, the
height never moved).

`min-h-touch` is on the controls now, so the floor holds at every width and no longer
depends on a rule scoped to another one. **The media query is deliberately left in
place** — it is a safety net for controls nobody has reached yet, and removing it is a
change with a blast radius far wider than one form.

### 5.1 The fix is the requirement's own ordering rule, not a spacing tweak

turns out. `PageShell` renders header `actions` **between** the page title and the
children, and below `md` it stacks them on their own row — so the dashboard's
*Refresh* control cost **60 px** (a 16 px gap plus a 44 px full-width button) directly
above the student's next action at 320 px.

R16.5 puts passive controls **after** the next required action, and a Refresh button
is not the student's next action. It is now the first control below the panel: same
page, same behaviour, one tap away, and no longer between the student and what they
came to do. It is also `w-auto` rather than `w-full` — a full-width utility button
reads as a primary action, which is the competition R16.3 forbids.

Trimming padding would also have bought the ~19 px needed. It was rejected on
purpose: the next slightly longer server-published label re-breaks it. Removing 60 px
of chrome leaves real headroom, and the number says so.

## 6. What was converted, what was fixed twice, and what was withdrawn

### 6.1 GATE-13.3-10 — three separate causes, and one attempt that was rolled back

**Cause 1 — the message.** `ErrorBoundary`'s section fallback piped
`state.error?.message` straight into copy. It now classifies the exception through
**`src/lib/errorBoundaryCopy.ts`** (new, pure, dependency-free): four sentences —
`offline` / `chunk` / `network` / `unknown` — none of which can contain an exception,
with `unknown` deliberately the default so the platform never tells a student their
connection failed when it did not. The exception still reaches
`reportBoundaryError` and `onError`, which is where a stack trace belongs.

**Cause 2 — why it was a `TypeError` at all.**
`lazy(() => import(m).then((mod) => ({ default: mod.SessionMonitor })))` reads a
property off whatever the loader returned, so a failed fetch became *"Cannot read
properties of undefined (reading 'SessionMonitor')"* — which also defeated
`LazyLoadErrorBoundary`'s own `isChunkError` classifier, so the app's chunk-recovery
path never ran either. `lazyNamed` in `AuthenticatedRouteShell.tsx` throws a named
chunk-load error instead.

**Cause 3 — an attempt that made things worse, and was withdrawn.** `SessionMonitor`
is a background session watcher that renders nothing, mounted as a *sibling* of the
route boundary, so its chunk failing took the whole authenticated tree with it. L6
gave it its own `<ErrorBoundary fallback={null}>`. That required fixing a real bug in
the primitive — `if (this.props.fallback)` treats `null` as *"no fallback given"*, so
`fallback={null}` rendered the **default** fallback; it is
`'fallback' in this.props && this.props.fallback !== undefined` now — and then the
measurement said the result was **worse**: with that subtree silent, the only thing
left after an offline chunk failure was the wizard route's own `Suspense` skeleton, a
page that spins forever with **no recovery control at all**
(`{"wizardUsableAgain":false,"retryAffordance":[]}` after reconnect, both profiles).

So it was rolled back, with the reasoning left in the source. A recovery affordance
the student can use beats a mount they cannot use.

**Measured after:**

```
"You appear to be offline  We could not reach the network, so this part of the page
 could not load.  Anything you had already saved is safe.  Reconnect and try again.
 Try Again  Contact Support"

namesTheConnection: true      leaksInternalError: false
```

**The residual, stated rather than implied.** `wizardStillMounted` is still `false`,
and it stays **recorded rather than asserted** — which is what 13.3 did with the same
measurement. `pages/student/applicationWizard/index.tsx` wraps the whole wizard in its
own `ErrorBoundary level="section"`, and when a chunk the *wizard* needs cannot be
fetched there is no code to render. The platform ships **no service worker** —
`vite-plugin-pwa` and the Workbox caches were removed outright
(`.kiro/steering/tech.md`) — so an un-cached chunk on a dead connection is genuinely
unavailable. A boundary cannot keep a form mounted whose code is not there. What
protects the student is the draft, not the DOM: auto-save is mandatory, the draft is
an `Application(status='draft')` row plus a local recovery snapshot, the copy now says
so, and the recovery leg asserts that `Try Again` after reconnect brings the wizard
back.

Also filed here rather than dropped: **a silent boundary over a lazily-loaded global
leaves the route as a permanent skeleton with no recovery control.** That failure mode
was discovered by the experiment above and does not exist in the shipped tree; it is a
trap for whoever next tries to isolate a lazy global, and it belongs to the shell lane.
