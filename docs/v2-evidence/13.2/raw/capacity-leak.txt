Reading: several intakes share one NAME and carry DIFFERENT max_capacity.
`Intake.objects.filter(name=app.intake, is_active=True).first()` has no
ordering, so which row it returns is whatever Postgres yields first — and the
staff read of an application publishes that row's capacity as if it were the
application's own. Both tenants' applications therefore report the same number,
and the row it lands on is not stable: in the recording above tenant A's
application reported 97 (tenant B's configured value), and an earlier recording in
the same session showed the converse - tenant B's application reporting 41, tenant
A's value. Either way the number does not belong to the application it is
published on.

Not a data-integrity hole: `applications.intake_id` is correct in every row
(Gate 2, zero mismatches), and the capacity a *decision* uses comes from
`ProgramIntake` under a row lock (CapacityService). What leaks is a number on a
staff screen — which is still a cross-tenant read, and is still the thing
`docs/canonical-truth-map.md` forbids: 'canonical IDs are the sole authority ...;
the legacy applications.institution/program/intake strings are display snapshots
only'.

The fix is one line — resolve through `a.intake_id` instead of `a.intake` — and
it is NOT applied here: this bullet runs and records.
